# RISK POLICY

**Config sources:** `config/risk_limits.json`, `config/runtime.yaml`  
**Last updated:** 2026-06-05  
**Authority:** This document describes enforced limits — the code implements them. Discrepancies between this document and `config/risk_limits.json` must be resolved by updating the config, not this document.

---

## Risk Mode Classification

The risk engine (`execution/risk_engine_v6.py`) classifies the portfolio into one of four modes every cycle. Classification is checked in strict severity order — the first match wins:

| Priority | Mode | Trigger condition | Effect |
|----------|------|-------------------|--------|
| 1 | HALTED | NAV age > 90s **or** NAV sources_ok=false **or** config load failed | All execution suspended |
| 2 | DEFENSIVE | DD ≥ 30% **or** daily loss ≥ 10% of NAV | New entries blocked; exits processed |
| 3 | WARN | Router degraded **or** maker-first disabled >5 cycles **or** fallback ratio > 0.50 | Execution continues; alerts emitted |
| 4 | OK | None of the above | Normal execution |

**Important:** "crisis" is not a `RiskMode` trigger. Crisis is handled at the Doctrine layer (`VETO_CRISIS`, `CRISIS_OVERRIDE`). The risk engine only classifies based on NAV health, drawdown, and execution quality.

## Portfolio-Level Limits

There are **two separate loss-limit systems** — they enforce different things and must not be conflated:

**Order-veto limits** (`config/risk_limits.json` → `execution/risk_limits.py`): Per-cycle checks that veto individual orders.

| Limit | Threshold | Enforcement |
|-------|-----------|-------------|
| Daily loss | 1% NAV | Veto new entry orders |
| Weekly loss | 3% NAV | Veto new entry orders |
| Max drawdown | 30% from peak | Veto new entry orders |
| Max portfolio leverage | 4× | Hard cap on all orders |
| Min notional per order | $25 | Hard minimum |

**Risk mode thresholds** (`execution/risk_engine_v6.py`): Classify overall system state.

| Threshold | Value | Effect |
|-----------|-------|--------|
| NAV stale | > 90s | HALTED |
| Drawdown for DEFENSIVE | ≥ 30% | DEFENSIVE mode |
| Daily loss for DEFENSIVE | ≥ 10% NAV | DEFENSIVE mode |
| Fallback ratio for WARN | > 0.50 | WARN mode |

| Other limit | Value | Source |
|-------------|-------|--------|
| NAV freshness (dashboard) | 150s | `config/risk_limits.json` |
| TWAP trigger threshold | $500 notional | `config/runtime.yaml` |

## Position Sizing

Sizing uses inverse-volatility scaling with adaptive factors:

```
notional = base_allocation × risk_factor × atr_factor × dd_factor × perf_factor
leverage  = min(target_leverage, symbol_max_leverage)
```

**Volatility regime scaling:**
| ATR regime | Size multiplier |
|-----------|----------------|
| Very High | 0.25× |
| High | 0.50× |
| Normal | 1.00× |
| Low | 0.75× |

Min notional per order: **$25** (global hard floor from `config/risk_limits.json`). The $500 figure is the TWAP trigger threshold — orders below $500 notional are sent as single limit orders rather than split into TWAP slices.

## Stop Logic

Exits are generated by `execution/exit_scanner.py` and resolved by the Doctrine Kernel (`execution/doctrine_kernel.py`). Precedence is strict — highest-priority reason wins:

| Priority | Exit reason | Urgency | Condition |
|----------|-------------|---------|-----------|
| 1 | `CRISIS_OVERRIDE` | Immediate | crisis_flag set or regime == CRISIS |
| 2 | `REGIME_FLIP` | Immediate | Regime reversed against position |
| 2 | `REGIME_CONFIDENCE_COLLAPSE` | Stepped | Regime confidence below 0.45 |
| 3 | `TREND_DECAY` | Stepped | Trend thesis eroded |
| 3 | `CARRY_DISAPPEARED` | Stepped | Mean reversion carry vanished |
| 3 | `CROSSFIRE_RESOLVED` | Stepped | Crossfire condition resolved |
| 3 | `EXECUTION_ALPHA_DRAG` | Stepped | Execution costs eating alpha |
| 4 | `TIME_STOP` | Patient | Position age > 96 bars (~24h on 15m) |
| 5 | `STOP_LOSS_SEATBELT` | Immediate | Emergency stop-loss threshold hit (last resort) |

Doctrine exit events are logged to **`logs/doctrine_events.jsonl`** (not `logs/execution/`).  
Risk-layer vetoes on new entries are logged to `logs/execution/risk_vetoes.jsonl`.

## Emergency Halt Conditions

The executor will suspend **all new order placement** (and optionally close all positions) under:

- Risk mode = HALTED (NAV missing, corrupt, or stale)
- Drawdown ≥ 30% from NAV peak
- Sentinel-X CRISIS_OVERRIDE across all symbols simultaneously
- Manual halt via supervisor: `supervisorctl stop hedge-executor`

**Cooldown after halt:** 30 minutes minimum before re-entry is permitted.

## Order Execution Controls

| Control | Setting |
|---------|---------|
| Order type | POST_ONLY (maker-first), taker fallback after 4 rejects |
| TWAP | Enabled; ≥4 slices, 10s intervals, min notional $500 |
| Slippage model | EWMA halflife=50 trades; expected ≤15 bps; depth=5 levels |
| Churn guard | 120s min hold, 300s cooldown per symbol |
| Exit dedup | 300s TTL per (symbol, side, reason) tuple |
| Fee buffer | 1.5× taker rate before entry approval |

## Logging Requirements

Every risk decision must be reconstructable:

| Event | Log location |
|-------|-------------|
| Risk vetoes (entry) | `logs/execution/risk_vetoes.jsonl` |
| Doctrine verdicts | **`logs/doctrine_events.jsonl`** |
| Fee gate verdicts | `logs/execution/fee_gate_events.jsonl` |
| Risk mode snapshots | `logs/state/risk_snapshot.json` |
| NAV history | **`logs/nav_log.json`** (unbounded JSON array — no auto-truncation) |

If a log entry is missing for any order that was attempted or placed, that is a **P1 logging audit failure**.
